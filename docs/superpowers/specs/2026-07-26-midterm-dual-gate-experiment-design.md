# 未知环境自主探索与路径规划双门槛实验设计（三分之一规模）

## 状态

- 设计日期：2026-07-26
- 设计状态：已确认，2026-07-26 按用户要求缩减到原方案约三分之一
- 当前阶段：仅固化实验与验收设计，尚未进入实现和正式运行
- 规模合同：`midterm_one_third_update80/v1`
- 适用指标：
  - 未知环境自主探索覆盖率：中期不低于 80%，完成时不低于 99%
  - 路径规划处理时间：中期不高于 2 s，完成时不高于 1 s

论文和专利不属于本设计范围。本设计不把投稿、专利申请或相关材料作为实验门槛或交付物。

## 1. 背景与设计目标

课题中期工作稿已经建立覆盖率计算、离线闭环运行、三类平台路径规划和结构化结果记录的技术基础，但尚未在统一场景、固定硬件、统一统计口径和预先冻结的正式测试条件下形成指标结论。

现有工程证据只能作为设计输入：

- PPO High-Resolution Frontier Stage 6 的 update 80 验证记录在 16 个验证场景上给出平均最终覆盖率约 0.9910、固定预算成功率 1.0。本设计固定使用该 update 80，不等待 update 100。该结果来自验证集，正式 Test 和 Unseen 评价尚未完成，不能直接认定覆盖率指标通过。
- Path Planner v2 Gate 6 已定义 2 s 硬超时、Standard P95 不高于 250 ms 和 Kilometer P95 不高于 750 ms 的工程目标，但正式配置仍因独立标签、独立最优解和正式请求清单缺失而处于 blocked 状态。

本设计的目标是复用上述技术基础，建立一次设计、两级门槛、分项资格试验和闭环交叉核验相结合的中期缩减规模实验链。场景数和规划请求数在接触正式结果前一次性冻结为原方案约三分之一；正式结果产生后不得继续缩小场景、更换分母、删除慢样本或混合平台结果来制造达标结论。

## 2. 范围与硬边界

### 2.1 范围

本设计包括：

1. G1 轮式平台未知环境自主探索覆盖率资格试验。
2. G2 轮式、足式和飞跃式平台路径规划处理时间资格试验。
3. G3 三模块闭环交叉核验。
4. 双门槛汇总、证据复算和结果路由。
5. 形成三分之一规模的中期技术资格证据；该证据不得表述为原每个正式 split 64 场景/1950 次规划调用方案的全规模替代。

### 2.2 不在范围内

本设计不包括：

- 论文或专利成果形成。
- checkpoint 发布。
- default policy 替换。
- 实物执行器接入。
- canary 或在线流量。
- 底层运动控制和实时通信验证。
- 将合成地形或仿真代理描述为真实物理障碍或实物平台结果。

### 2.3 长期技术边界

- 默认 A* 不因本实验被替换。
- Hybrid A* 保持 opt-in 路径代价或位姿规划来源，不宣称 Ackermann feasible。
- 足式与飞跃式结果保持 simulation proxy 边界。
- 平台硬坡度阈值保持 `max_traversable_slope_deg=30.0`。
- G1、G2 和 G3 只消费冻结后的算法、配置、场景和模型，不在正式测试过程中训练或修改算法。

## 3. 总体验收结构

采用三门结构：

| 门 | 主要对象 | 中期门槛 | 完成时门槛 | 结论作用 |
| --- | --- | --- | --- | --- |
| G1 | 轮式平台自主探索覆盖率 | 覆盖率不低于 80% | 覆盖率不低于 99% | 覆盖率指标资格结论 |
| G2 | 三类平台规划处理时间 | 各平台均不高于 2 s | 各平台均不高于 1 s | 处理时间指标资格结论 |
| G3 | 建模、决策、规划和观测更新闭环 | 组合运行不破坏 80%/2 s | 组合运行不破坏 99%/1 s | 系统级交叉核验 |

总体判定为：

```text
midterm_one_third_gate_passed =
  g1_coverage_80_passed
  AND g2_all_platforms_2s_passed
  AND g3_midterm_crosscheck_passed

final_threshold_one_third_gate_passed =
  g1_coverage_99_passed
  AND g2_all_platforms_1s_passed
  AND g3_final_crosscheck_passed
```

G3 不替代 G1 或 G2。G3 失败时，G1 和 G2 的独立结果仍保留，但不得形成“系统闭环同时满足双门槛”的结论。

### 3.1 三分之一规模与一天执行边界

本版按下列整数合同实现原方案约三分之一规模：

- G1 首次正式评价为 Test-Q21 和 Unseen-21，共 42 个 episode；失败确认集为 Test-C21。
- G2 为 3 个平台、每个平台 43 个请求、每个请求 5 次重复，共 645 次正式规划调用。
- G3 为 10 个轮式闭环 episode，并对足式和飞跃式各执行 3 次短接口回放。
- 80%/2 s、99%/1 s、安全约束、失败语义、统计方法和证据完整性要求不随规模缩减。

对应首轮规模比例为：G1 `42/128=32.8125%`，G2 `645/1950≈33.08%`，G3 `16/48=33.3333%`。Test-C21 只属于失败后的独立确认分支，不计入首轮规模。

`final_threshold_one_third_gate_passed` 只表示同一三分之一规模实验达到了 99%/1 s 数值阈值，不等同于项目全规模完成验收。所有结果、字段和报告都必须同时携带规模合同，不得生成省略 `one_third` 限定的通过别名。

在 update 80、正式输入、runner 和缓存均已就绪且无失败重跑的前提下，正式运行预计需要 14～18 小时，按不超过 20 小时的连续窗口排期。该时间预算不包含 G2 独立输入生产、runner 实现、缺陷修复或 Test-Q21 失败后的 Test-C21 重跑。G2 正式计时期间禁止并发运行训练、覆盖率评价或其他高负载任务。

## 5. G1 覆盖率资格试验

### 5.1 正式平台与场景

G1 以当前闭环成熟度最高的轮式平台作为正式覆盖率平台。足式和飞跃式不与轮式覆盖率混合统计。

场景使用 Standard v1：

- ROI：128 m × 128 m。
- 高分辨率表征：0.5 m/cell，256 × 256。
- 低分辨率全局表征：4 m/cell，32 × 32。
- 固定最大决策步数：128。
- 达到 99% 后允许结束，但达到 80% 时不得提前结束。
- 停滞终止、无候选终止和其他终止原因保持冻结配置。

正式场景集：

| 集合 | 数量 | 用途 |
| --- | ---: | --- |
| Validation | 现有 150 个目录中的固定子集 | checkpoint 选择、阈值预检和开发诊断 |
| Test-Q21 | 21 | 第一次正式资格试验 |
| Test-C21 | 21 | Test-Q21 失败并完成修复后的独立确认集 |
| Unseen-21 | 21 | Test-Q21 通过后的未见场景泛化试验 |

Test-Q21、Test-C21 和 Unseen-21 不参与模型更新或 checkpoint 选择。Test-C21 从 Test 目录未用于 Test-Q21 的场景中预先冻结。若 Test-Q21 失败，修复只能使用 Train 和 Validation；下一版本使用 Test-C21，不允许反复调试 Test-Q21。

场景清单按以下因素分层：

- 坡度分布。
- 障碍密度。
- 初始位姿。
- 初始观测范围。
- 候选稀疏程度。
- 可覆盖区域规模。

### 5.2 覆盖率分母

正式分母为：

```text
coverage_denominator_source =
  reachable_observable_free_highres_cells/v1
```

对场景 \(i\)，有效可覆盖集合为 \(\Omega_v^{(i)}\)，终止时累计覆盖集合为 \(\Omega_c^{(i)}(T_i)\)，最终覆盖率为：

```text
coverage_i =
  area(Ωc_i(T_i) intersect Ωv_i)
  / area(Ωv_i)
```

分母必须满足：

- 位于固定 ROI 内。
- 不属于硬障碍或明确不安全区域。
- 对活动轮式平台可达。
- 在冻结传感器模型下可观测。
- 在正式运行前确定并写入掩膜哈希。

隐藏真值只能用于环境记账、终止判定和最终评价，不得成为策略空间输入、候选筛选捷径或 baseline 的未来信息。

`main_coverable_cells/v1` 只有在集合成员、单元数量和 SHA-256 与上述分母完全一致时，才允许作为语义别名记录。无法证明完全一致时，两个名称必须分开报告。

每个场景保存：

- 分母单元数和面积。
- 初始覆盖单元数和覆盖率。
- 每步新增覆盖和累计覆盖。
- 重复观测去重结果。
- 分母掩膜及其哈希。
- 分母来源、可达性来源和可观测性来源。

分母为空、哈希漂移或来源不完整时，该场景判为无效并阻塞整次正式运行，不得从统计中静默剔除。

### 5.3 策略与运行协议

- checkpoint 仅按 Validation 的 `success_rate_under_fixed_step_budget` 选择；平均最终覆盖率只作为固定 tie-break。
- 正式评价使用确定性策略：
  - 候选动作为掩膜后的 logits 最大项。
  - theta 使用选中候选的策略均值。
- Test-Q21 和 Unseen-21 使用相同模型、候选生成器、传感器、规划后端、预算和终止规则。
- 正式评价继续使用 8 个 worker；21 个场景按固定 lane 大小 `(3,3,3,3,3,2,2,2)` 分配，不根据运行速度动态重排。
- 所有 episode 保存动作、候选、路线、覆盖曲线、终止状态和失败原因。
- Test 与 Unseen 的场景级结果分别统计，不合并后再判定。

### 5.4 双门槛与统计

正式主指标为每个 split 的场景宏平均最终覆盖率。内部稳健性门槛同时约束达到对应阈值的场景比例。

| 判定项 | 中期门槛 | 完成时门槛 |
| --- | ---: | ---: |
| Test-Q21 平均最终覆盖率 | ≥ 0.80 | ≥ 0.99 |
| Unseen-21 平均最终覆盖率 | ≥ 0.80 | ≥ 0.99 |
| Test-Q21 达标场景数 | ≥ 20/21 | ≥ 20/21 |
| Unseen-21 达标场景数 | ≥ 20/21 | ≥ 20/21 |
| 掩膜外动作数 | 0 | 0 |
| 安全违规数 | 0 | 0 |

同时报告：

- 场景平均值、中位数、样本标准差、最小值和最大值。
- 达到 80% 与 99% 的场景比例。
- 固定种子的 2000 次 episode bootstrap 95% 置信区间。
- 覆盖曲线面积。
- 达到 80% 和 99% 所需步数与路程。
- 单位路程覆盖收益。
- 无效动作、规划失败、重规划和各类终止次数。

Bootstrap 以 episode 为抽样单位，不以 step 为抽样单位。置信区间用于表达不确定性，不替代预先定义的点估计和场景比例门槛。

### 5.5 G1 执行顺序

1. 在 3 个 Validation 场景执行 dry-run，验证接口和证据格式。
2. 冻结 checkpoint、有效配置、场景清单和分母哈希。
3. 一次性运行 Test-Q21。
4. Test-Q21 通过后一次性运行 Unseen-21。
5. 固定抽取 3 个场景重复回放，要求动作、覆盖曲线和终止状态一致。
6. 从逐场景结果独立复算 summary。
7. 输出 G1 报告和路由。

## 6. G2 三平台规划计时资格试验

### 6.1 正式样本矩阵

轮式、足式和飞跃式平台分别建立正式数据集和结果。

每个平台的唯一请求：

| 场景集 | 请求数 | 构成 |
| --- | ---: | --- |
| Standard | 33 | 23 个可达、7 个困难可达、3 个独立标注不可达 |
| Kilometer/压力集 | 10 | 6 个可达、2 个困难可达、2 个不可达或边界条件 |

每个请求重复 5 次，固定随机种子改变请求顺序但不改变请求内容。正式计时样本总数为：

```text
3 platforms × 43 requests × 5 repeats = 645 calls
```

请求必须通过结构 schema。字段缺失、越界坐标和类型错误等输入校验用例单独运行，不得混入正式规划时间样本。

相同地形与起终点尽量跨平台配对，但以下内容必须按平台独立：

- 可达性标签。
- 平台能力参数。
- 运动原语。
- 路线完整性判据。
- 结果与统计。

### 6.2 正式独立输入

复用 Path Planner v2 Gate 6 前，必须补齐：

- 每个平台不少于 3334 条独立运动原语安全标签。
- 每个平台至少 1 组小地图独立最优解。
- 每个平台 33 个 Standard 请求。
- 每个平台 10 个 Kilometer 请求。
- 每个请求的独立可达性标签、稳定请求 ID、请求 SHA-256 和来源标识。
- 若直接使用 Gate 6 全合同，每个平台至少 1 个 PPO 目标与请求绑定。

独立 oracle、人工标注或独立求解器不得与被测 provider 使用同一个安全判定实现。来源标识必须证明 oracle 与 provider 相互独立。

### 6.3 正确性与安全前置门槛

路径规划时间达标不能抵消路线错误。正式时间统计同时要求：

- 不可行路线误接收数为 0。
- 独立标注可达请求的 provider 成功率不低于 0.99。
- 成功路线的完整 L2 复核比例为 1.0。
- 未知或证据不足状态不得接收为成功。
- 超时结果不得携带成功路线。

足式保持 `simulation_proxy_static_crawl/v1` 等已冻结代理能力边界；飞跃式保持弹道与着陆代理边界。二者不宣称动态步态、真实机器人稳定性或实物弹跳可行性。

### 6.4 计时边界

使用 `time.perf_counter_ns()`。单次规划处理时间从完整请求进入内存并开始处理时起，到形成完整路线结果或结构化未完成结果时止。

计时包括：

- 输入有效性检查。
- 平台约束实例化。
- 路线搜索。
- 完整路线复核。
- 结构化结果组织。

计时不包括：

- 进程启动。
- 正式输入文件读取。
- 外部通信和队列等待。
- 图形绘制。
- 日志落盘。

每个正式样本同时保存以下分阶段时间：

- input_validation。
- platform_instantiation。
- search。
- complete_route_validation。
- result_assembly。

各阶段之和必须与总计时在规定舍入误差内一致。

### 6.5 预热、并行和缓存

- 每个平台先执行 10 个不属于正式集的预热请求。
- 正式配置使用 `worker_count=4`。
- `worker_count=1` 作为解释性对照，不用于替换正式配置结果。
- 可复用静态地形、层次图和安全验证缓存。
- 禁止缓存完整请求的路线答案。
- 缓存键、命中率、构建来源和内容哈希必须进入 cache audit。
- 冷启动首请求时间单独报告，不混入稳态正式分布。

固定记录：

- CPU 线程数和亲和性设置。
- 操作系统电源模式。
- Python hash seed。
- 后台负载检查。
- worker 启动方式。
- 缓存是否只读和是否跨请求复用。

### 6.6 双门槛

每个平台、每种规模、成功结果和结构化未完成结果分别统计。总体 G2 判定取最差平台和最差正式规模。

| 指标 | 中期门槛 | 完成时门槛 |
| --- | ---: | ---: |
| 平均处理时间 | ≤ 2000 ms | ≤ 1000 ms |
| P95 处理时间 | ≤ 2000 ms | ≤ 1000 ms |
| 阈值内完成比例 | 100% 在 2000 ms 内 | ≥ 95% 在 1000 ms 内 |
| 绝对硬超时 | 0 个样本超过 2000 ms | 0 个样本超过 2000 ms |

P95 使用预先冻结的 nearest-rank 算法。报告样本数、平均值、中位数、P95、P99、样本标准差、最小值、最大值以及固定种子的 bootstrap 95% 置信区间。

每个平台的 Standard 分布包含 165 个正式计时样本，Kilometer 分布包含 50 个正式计时样本。不得将两个规模或不同平台合并后计算 P95。

保留 Gate 6 的更严格工程余量目标：

- Standard P95 不高于 250 ms。
- Kilometer P95 不高于 750 ms。
- 超过 2000 ms 的样本数为 0。

工程余量目标用于降低运行环境波动对 1 s 完成时门槛的影响，不替代正式 1 s 统计。

### 6.7 未达标时的诊断顺序

未达标时只使用非正式开发集：

1. 根据分阶段时间定位输入、搜索、验证或结果组织瓶颈。
2. 单因素比较多启发式、层次搜索、惰性验证和安全缓存。
3. 比较 `worker_count=1/4` 并验证结果语义等价。
4. 调整运动原语分辨率时重新执行完整安全复核。
5. 冻结新版本，使用未见请求重新进行正式计时。

任何优化不得静默放宽硬约束、减少完整验证、改变失败语义或把未完成路线变为成功。

## 7. G3 闭环交叉核验

### 7.1 场景

在正式运行前预先固定 10 个轮式闭环场景：

- Test-Q21 中 5 个。
- Unseen-21 中 5 个。
- 覆盖不同坡度、障碍密度、规划距离和候选稀疏度。

选择清单不得根据 G1 或 G2 结果重新生成。

另对足式和飞跃式各执行 3 个短闭环接口回放，只检查请求对应、结构化反馈和实际调用耗时，不与轮式覆盖率混合。

### 7.2 数据流

每个轮式场景执行：

```text
约束建模
→ 候选生成
→ 策略选择
→ 路径规划
→ 完整路线复核
→ 状态推进
→ 观测更新
→ 下一轮决策
```

每一轮保存：

- 环境快照 ID 和 SHA-256。
- 候选集合及有效掩膜。
- 选定候选、位置和 theta。
- 规划请求 ID。
- 路线或结构化未完成结果。
- 路线反馈和失败原因。
- 覆盖增量。
- 规划调用总时间和阶段时间。
- 后继环境状态。

### 7.3 通过条件

- 10 个轮式场景的平均最终覆盖率满足对应的 80% 或 99% 门槛。
- 达到对应阈值的场景比例不低于 95%；在 10 个场景下等价于 10/10 均达到对应阈值。
- 每次规划调用保留 G2 计时边界，P95 满足对应的 2 s 或 1 s 门槛。
- 超过 2 s、掩膜外动作、安全违规和候选—路线错配均为 0。
- 与 G1 相同场景的最终覆盖率配对差值平均不低于 -1 个百分点。
- 无效目标、不可达路线和预算耗尽返回稳定原因码，不以部分路线冒充成功。
- 足式和飞跃式接口回放的平台标识、请求、路线结果和失败状态保持对应。

### 7.4 故障回放

附加固定用例：

1. 当前状态无有效候选。
2. 已选目标在规划时变为不可达。
3. 规划达到 2 s 硬截止时间。
4. 环境快照或请求版本过期。

系统必须安全终止或重新选择，并记录稳定原因码；不得无限重规划、静默放宽约束或继续使用过期路线。

## 10. 错误处理与可恢复执行

- 每个 phase 在完成后追加 `phase-state.jsonl`。
- 恢复执行只接受连续、完整且哈希有效的 phase 前缀。
- 不完整 phase 必须重新运行，不拼接部分统计。
- 超时、异常和结构化未完成结果均写入 `results.jsonl`。
- manifest 或输入哈希漂移时立即阻塞。
- 正式输出目录已存在时禁止覆盖。
- 样本丢失、重复 ID、平台错配或 split 泄漏时立即阻塞。
- 所有数值必须有限；NaN 和 inf 使对应门 blocked。
